# Формат YAML цифровой схемы

YAML описывает геометрию и связи, а не исполняемую электрическую модель.
Файл читается в UTF-8 через `yaml.safe_load`. Используйте пробелы для отступов.
ID блоков/выводов чувствительны к регистру; лучше использовать короткие ASCII-имена
без точек. Визуальные подписи могут содержать русский текст.

## Корневая структура

```yaml
canvas: {}       # настройки изображения и маршрутизации
blocks: {}       # ID блока -> описание
ports: {}        # внешние прямоугольные IN/OUT-блоки, необязательно
connections: [] # список электрических связей
net_names: {}    # имя вывода -> имя электрической сети, необязательно
primitives: []   # дополнительная графика, необязательно
```

Секции можно опускать, но без блоков/портов получится пустой рисунок.
Пользовательские секции `design`, `contract`, `widths` из примеров являются
метаданными: рендерер не исполняет их и не проверяет автоматически соответствие
битовых разрядностей. `layout_groups` читает только этап подготовки ELK.

## Рабочий небольшой пример

```yaml
canvas:
  layout: grid
  wiring: routed
  scale: 2
  column_gap: 100

blocks:
  G1:
    symbol: NOT
    position: [1, 0]
    inputs: [A]
    outputs: [Q]

ports:
  IN_A:
    label: A
    direction: input
    position: [0, 0]
  OUT_Y:
    label: Y
    direction: output
    position: [2, 0]

connections:
  - IN_A -> G1.A
  - G1.Q -> OUT_Y
```

Сохранённый файл рендерится командой:

```powershell
.venv\Scripts\python.exe -m schematic_renderer example.yaml -o output/example.png
```

Реальные готовые файлы находятся в [examples](../examples).

## Блоки

```yaml
blocks:
  RG1:
    symbol: RG
    label: "15 bit"
    position: [0, 0]
    offset: [0, 0]
    min_width: 220
    min_height: 160
    inputs:
      - {name: D, label: "D:s15"}
      - {name: LD, label: LOAD}
      - {name: C, label: CLK, marker: clock}
      - {name: R, label: RESET}
    outputs:
      - {name: Q, label: "Q:s15"}
```

| Поле | Назначение |
| --- | --- |
| `RG1` | Уникальный ID; печатается над блоком и используется в соединениях. |
| `symbol` | Центральное обозначение: RG, SM, MX, CT, AND, OR, XOR, NOT или любой текст. По умолчанию ID. |
| `label` | Дополнительная подпись внутри блока, например разрядность. |
| `position` | `[колонка, строка]` для grid; `[x, y]` для absolute. По умолчанию `[0,0]`. |
| `offset` | Дополнительное смещение `[dx,dy]` в координатах рисунка. |
| `min_width`, `min_height` | Минимальные размеры; подписи и выводы могут увеличить блок. |
| `inputs`, `outputs` | Списки выводов. Их функции не определяются символом автоматически. |

RG не получает CLK/LD/RESET сам по себе: перечисляйте требуемые входы явно.
Аналогично у сумматора нужно самому определить вход переноса, SUB и выходы,
если они требуются архитектурой. Отсутствие электрически обязательного входа
рендерер сам не распознаёт.

## Выводы и шины

```yaml
inputs:
  - A
  - {name: C, label: CLK, side: left, order: 2, marker: clock}
  - {name: R, label: /RESET, marker: invert}
outputs:
  - {name: Q, label: "Q[14:0]", side: right}
```

- `name`: ID вывода для ссылки `BLOCK.PIN`.
- `label`: отображаемый текст; по умолчанию равен `name`.
- `side`: left/right/top/bottom. Входы по умолчанию слева, выходы справа.
- `order`: порядок на выбранной стороне; по умолчанию индекс в списке.
- `marker: clock` или `clk`: треугольник тактового входа; `invert`: кружок инверсии.

Имена выводов должны быть уникальными внутри блока, в том числе между входами
и выходами. Для максимальной переносимости используйте латинские значения
side/marker. В named-режиме и в подготовке ELK разрешены только left/right.

**Один вывод-шина** задаётся отображаемой подписью в mapping:

```yaml
inputs:
  - {name: D, label: "D[14:0]"}
```

Ссылка на него: `RG1.D`. Нельзя обращаться к `RG1.D0`: такого вывода нет.
Для раздельных битовых выводов используется строковое сокращение:

```yaml
inputs: ["D[0:14]"]
```

Оно разворачивается в D0, D1, ..., D14. Обратный диапазон также поддерживается.
Строки, похожие на YAML-числа/логические значения (`ON`, `OFF`, `0`), берите
в кавычки, чтобы они не превратились в другие типы данных.

## Соединения

Рекомендуемый стиль: **один источник и один приёмник на запись**.

```yaml
connections:
  - RG1.Q -> SM1.A
  - {from: RG2.Q, to: SM1.B}
  - {chain: "SM1.Q -> RY.D"}
```

Разветвление записывается отдельными связями от того же источника:

```yaml
connections:
  - CTRL.CLK -> RG1.C
  - CTRL.CLK -> RG2.C
  - CTRL.CLK -> RY.C
```

Укажите ID, а не подпись. `RG1.Q` означает вывод Q блока RG1; имя порта
пишется без точки. Имя блока без вывода допустимо только для блока с одним
выводом. Парсер также принимает длинные `chain`, но для переносимости между
режимами и для однозначного ветвления используйте двухконечные записи.

Рендерер проверяет существование ссылок, но не является ERC-проверкой:
направление output -> input, отсутствие нескольких драйверов, согласование
ширины шин и наличие CLK/RESET должны проверяться автором либо отдельными тестами.

## Три режима проводов

| `canvas.wiring` | Поведение |
| --- | --- |
| `routed` | Встроенная ортогональная маршрутизация небольших схем. Размещение блоков задаётся вручную. |
| `named` | Короткие линии с именами сетей. Одинаковые имена на рисунке обозначают связь, длинных проводов нет. |
| `connected` | Непрерывные провода по сохранённым точкам. Пересечения разных сетей отображаются перемычками, ветвления одной сети точками. |

`routed` стремится не пересекать другие сети и может не найти путь в плотной
схеме. Для единого чертежа со многими связями используйте ELK и `connected`.

### Явные точки

```yaml
connections:
  - from: RG1.Q
    to: SM1.A
    points: [[360, 124], [400, 124], [400, 224], [500, 224]]
```

Все точки заданы в абсолютных координатах **до** применения `scale`.
Концы у выводов добавляются автоматически. В `connected` каждая запись
обязана содержать ровно два вывода и непустой `points`; все отрезки, включая
подход к выводу, должны быть горизонтальными или вертикальными.
В `routed` ручные точки являются указаниями для маршрута, который ортогонализуется.

### Автоматическая подготовка

После `python install.py --layout`:

```powershell
.venv\Scripts\python.exe -m schematic_renderer.prepare source.yaml -o output/prepared.yaml
.venv\Scripts\python.exe -m schematic_renderer output/prepared.yaml -o output/prepared.png
```

ELK выставляет absolute/connected, размещает блоки слева направо, сохраняет
точки маршрутов и уплотняет чертёж без уменьшения символов. Текущая подготовка
работает только с `blocks`, без `ports`, и с left/right выводами.
Она удаляет старые `primitives`, поскольку их координаты становятся неверными.
Также есть отдельная команда уплотнения готового connected-файла:

```powershell
.venv\Scripts\python.exe -m schematic_renderer.compact input.yaml -o output/compact.yaml
```

Для группировки ELK можно задать `layout_groups: {cell1: [RG1, SM1]}`. Каждый
блок может находиться не более чем в одной группе; рамка группы не рисуется.
Встроенные учебные соглашения размещают блоки с ID RA/RB/RSYNC в начале,
RY/YSYNC/RERR в конце, CLOCK отдельно. Для других ID используются общие правила ELK.

## Имена сетей

```yaml
net_names:
  RG1.Q: A15
  CTRL.CLK: CLK
```

Имя распространяется по `connections`. Две несвязанные сети не могут иметь одно
имя, а одна сеть не может получить противоречивые имена. Поэтому одинаковые
подписи **сами не соединяют** выводы: связь должна существовать в `connections`.
В `connected` эти имена используются для проверки геометрии и контактов,
но не печатаются автоматически у каждого провода.

## Внешние сигналы

`ports` создаёт небольшие прямоугольные блоки IN/OUT, **не стрелки**:

```yaml
ports:
  INPUT_A:
    direction: input
    label: A
    position: [0, 0]
```

Для учебных внешних стрелок, как в функциональных примерах, используются
обычные пины с уникальными подписями IN_/OUT_ и наконечники из `primitives`.
`design.external_inputs`/`external_outputs` в этих примерах документируют
внешние терминалы; это соглашение примеров, не отдельный тип порта рендерера.
Посмотрите готовый [фиксированный умножитель](../examples/fixed15_functional/fixed15_functional.yaml).

## Холст и размеры

Основные поля `canvas` (в координатах до масштабирования):

| Поле | По умолчанию | Значение |
| --- | --- | --- |
| `layout` | grid | grid или absolute для блоков |
| `wiring` | routed | routed, named, connected |
| `scale` | 3 | Целочисленный масштаб экспорта; не меняет логические координаты |
| `background` | white | Цвет фона |
| `margin` | 40 | Поля |
| `width`, `height` | автоматически | Фиксированный размер, если указан |
| `font_size`, `small_font_size` | 16, 13 | Основной шрифт и подписи выводов |
| `line_width` | 2 | Толщина линий |
| `pin_length`, `pin_gap` | 18, 24 | Длина вывода и вертикальный шаг |
| `block_padding_x`, `block_padding_y` | 16, 16 | Внутренние отступы |
| `min_block_width`, `min_block_height` | 96, 72 | Минимальные размеры блоков |
| `column_gap`, `row_gap` | 160, 70 | Промежутки сетки |
| `route_step` | 20 | Шаг встроенного маршрутизатора |

Grid учитывает размеры текста; это не просто умножение индекса колонки на
фиксированный шаг. Поля `grid_x`, `grid_y` принимаются для совместимости,
но размеры ячеек определяются измерением блоков и промежутками выше.
Внешние `ports` размещаются сеткой; для absolute-схем предпочтительны пины блоков.
Большая схема требует большого изображения: не задавайте маленький width/height
для автоматического уменьшения, такого поведения нет. SVG позволяет масштабировать
изображение без потери качества. Изменение шрифта/размеров требует новых маршрутов.

## Графические примитивы

Поддерживаются только line, polyline, rect, text:

```yaml
primitives:
  - {type: line, from: [20, 20], to: [100, 20], width: 2}
  - {type: polyline, points: [[92, 15], [100, 20], [92, 25]], width: 2}
  - {type: rect, position: [20, 40], size: [180, 80], width: 1}
  - {type: text, position: [30, 60], text: "Label", font_size: 16}
```

По умолчанию цвет чёрный; переопределяется `color`. У rect только контур.
Примитивы рисуются перед блоками и проводами. Они не являются электрическими
соединениями и не учитываются полноценно валидатором маршрутов или автоматическим
расчётом границ: размещайте их внутри холста и отдельно проверяйте изображение.
Для рисунка без пояснений просто не добавляйте text-примитивы.

## Проверка

Рендер сам выполняет проверки парсера, размещения и выбранного маршрутизатора:

```powershell
.venv\Scripts\python.exe -m schematic_renderer your.yaml -o output/check.png
```

Отдельного CLI-флага `--validate` сейчас нет. В Python доступны `load_schematic`,
`make_layout`, `named_nets`, `connected_routes`. Проверяются ссылки, геометрия,
согласованность имён сетей; электрическая/арифметическая корректность требует
отдельной проверки. Не используйте дубли ключей YAML: безопасная загрузка YAML
сама по себе не гарантирует их обнаружение.
